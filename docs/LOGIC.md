# Как устроен перенос настроек (логика оригинального кода)

Документ для Дениса: простым языком, без жаргона разработчика.
Описывает **то, что реально делает код** в этом репозитории (копия Flight-Bridge 0.5.1).
Имена файлов и методов указаны в `` `обратных кавычках` ``, чтобы можно было сверить с исходниками.

---

## Что делает программа в двух словах

Flight Bridge находит профили управления из **MSFS 2020**, сопоставляет их с уже
существующими профилями **MSFS 2024** на том же устройстве и **переписывает файлы
профилей 2024 прямо в хранилище игры** (кнопки, оси). Перед записью делает полную
резервную копию хранилищ. Если что-то идёт не так — откатывает изменения.

Точка входа приложения — `App.Main` → `AutomaticApp.Run` (`src/App.cs`,
`src/AutomaticApp.cs`). Кнопка «Перенести настройки» вызывает
`MigrationTransaction.Execute` — то есть **запись в игру**, а не экспорт файла
для ручного импорта.

## 1. Как находятся обе игры и хранилища

Всё обнаружение — в `AutoMigration.Discover` (`src/AutoMigration.cs`).

### Steam

1. Путь Steam берётся из реестра:
   - `HKEY_CURRENT_USER\Software\Valve\Steam` → `SteamPath`, иначе
   - `HKEY_LOCAL_MACHINE\SOFTWARE\WOW6432Node\Valve\Steam` → `InstallPath`.
2. Список библиотек читается из `steamapps\libraryfolders.vdf` (поле `"path"`).
3. Ищутся приложения по AppID:
   - **2020** — `1250410`
   - **2024** — `2537590`
4. Для каждого AppID проверяется манифест `appmanifest_<id>.acf` и папка установки.
5. Профили лежат в `userdata\<steamId>\<appId>\remote\` в файлах вида
   `inputprofile_<число>` (допускается и `inputprofile_inputprofile_<число>`).
6. Активный аккаунт Steam: значение `ActiveUser` из
   `HKEY_CURRENT_USER\Software\Valve\Steam\ActiveProcess`. Установка помечается
   `Active=true`, если имя папки пользователя совпадает с этим номером.
7. Для пары Steam→Steam в `AutoMigration.Build` учитывается один и тот же
   `Account`. Если есть ровно одна пара, где оба магазина `Active`, берётся она;
   иначе при нескольких аккаунтах перенос блокируется сообщением про выбор аккаунта.

### Microsoft Store / Xbox WGS

Для каждого года строится путь под `%LocalAppData%\Packages\...`:

| Год  | Пакет Store |
|------|-------------|
| 2020 | `Microsoft.FlightSimulator_8wekyb3d8bbwe\SystemAppData\wgs` |
| 2024 | `Microsoft.Limitless_8wekyb3d8bbwe\SystemAppData\wgs` |

Обход файлов — `AutoMigration.SafeFiles`: рекурсивно, **без** перехода по
символическим ссылкам / reparse points (`CheckPath`). Файлы
`containers.index` и `container.*` **не читаются как профили**.

Смешанная установка (Steam с одной стороны, Store с другой) допускается:
пары строятся из любого 2020 + любого 2024, кроме случая «два разных Steam-аккаунта».

### Старый путь «только корни» (legacy)

`Engine.AutoRoots` (`src/Core.cs`) добавляет только:

- Store WGS **2020** (`Microsoft.FlightSimulator_...`),
- Steam `userdata\*\1250410\remote`.

**Корней для MSFS 2024 здесь нет.** Этот метод — наследие ручного/старого
сканирования; текущий UI им не пользуется (использует `AutoMigration.Discover`).

## 2. Как читаются профили

`Profile.Read` (`src/Core.cs`):

1. Отказ, если файл больше **8 МБ**.
2. XML читается с запретом DTD и лимитом символов 8 МБ.
3. Декларация `<?xml ...?>` в начале снимается регулярным выражением — дальше
   файл может быть **фрагментом** (несколько корневых элементов) или обычным
   документом.
4. Фрагмент оборачивается во внутренний контейнер `ProfileFragment`; признак
   фрагмента — наличие элементов `Device` на верхнем уровне.
5. Проверка: ровно один `Device`, и внутри есть `Context` или `Axes`.
6. Исходные байты файла сохраняются в `OriginalBytes` (для проверки «файл не
   изменился с момента чтения» через SHA-256).

Сохранение фрагмента (`Profile.Save`) снова пишет XML-декларацию и дочерние
узлы без обёртки — как в облачном формате Steam/WGS.

## 3. Как пары 2020 ↔ 2024 выбираются

Логика в `AutoMigration.CompatibleSources` и `AutoMigration.Build`.

### Сопоставление устройств — **не по GUID**

Устройство считается одним и тем же, если совпадают:

1. **`ProductID`** (число; допускаются строки вида `0x....`) — метод `Product`,
2. **`DeviceName`** после нормализации `Norm` (верхний регистр, только буквы и
   цифры; пробелы и знаки убираются).

GUID устройства в коде **нигде не сравнивается**. В диагностическом отчёте
`RedactedReport` даже явно говорится, что GUID в отчёт не попадают.

Дополнительно кандидат должен дать хотя бы одно скопированное назначение или ось
в пробном `Engine.Analyze(..., allowRelocated: true)`.

### Имя профиля (эвристики)

Среди совместимых по устройству:

1. Сначала ищут точное совпадение нормализованных имён (`Norm(s.Name) == Norm(t.Name)`).
2. Если не нашли и имя цели не короче 3 символов — допускают, что имя 2020
   **заканчивается** именем 2024 (например, длинное имя с приставкой устройства
   и короткое «R66»). Комментарий в коде это прямо описывает.
3. Если после этого ровно один кандидат — пара принимается.
4. Если 0 или больше одного — профиль 2024 **не трогают**, добавляют запись в
   `Notices` («безопасное соответствие не найдено»).
5. Заблокированные профили (`FriendlyName Locked="true"`) пропускаются.
6. Профиль без `FriendlyName` оставляют без изменений (notice про формат).

Итог: программа **не угадывает** при неоднозначности.

## 4. Как копируются кнопки и оси

Ядро — `Engine.Analyze` (`src/Core.cs`).

### Назначения (Action)

Для каждого `Action` в источнике, у которого есть `Primary` или `Secondary`:

1. Ищут в цели действие с **тем же `ActionName` и тем же `ContextName` родителя**.
2. Если не нашли и включён `allowRelocated`, а имя начинается с `KEY_` — ищут
   действие только по `ActionName` в любом контексте; перенос засчитывается как
   «relocated», только если нашлось **ровно одно** такое действие.
3. Если совпадений не ровно одно, действие уже использовано, или имя пустое —
   в `Skipped` («нет однозначного совпадения команды»).
4. У цели удаляются старые `Primary` / `Secondary` / `Axis`, копируются элементы
   из источника.
5. **`Flag`, `ValueEvent`, `Delay` цели (формат 2024) сохраняются.** Комментарий
   в коде: числовые флаги 2020 и 2024 несовместимы (например, ось `4` в 2020
   может быть `132` или `4100` в 2024). Переносятся только физические привязки
   клавиш/кнопок пользователя.
6. Автоматический UI всегда вызывает анализ с `allowRelocated: true`
   (`CompatibleSources` / `Build`).

### Оси (Axes)

Если у обоих профилей есть блок `Axes`, для каждой оси источника с тем же
`AxisName` в цели копируются **только те атрибуты, которые уже есть** у целевой
оси (значения обновляются, новые атрибуты не добавляются).

### Что пропускается

- Неоднозначные команды (0 или >1 совпадения) — `Skipped`.
- Неизвестный формат привязки (нет корректного `Flag` или нет потомка `KEY`).
- Общие команды меню/камер, которых **нет** в нужном контексте/категории
  профиля 2024: им просто не находится однозначная цель — они остаются как
  были в 2024 и попадают в список «требуют ручной настройки» / details.
- После копирования, если одна и та же комбинация клавиш в контексте оказалась
  на разных действиях, добавляется предупреждение «проверьте общую кнопку/ось».

Имя выходного профиля в ручном `Analyze` формируется как
`исходное имя · FB MMdd-HHmm-xxxx`, но в автоматическом режиме
`AutoMigration.Build` **возвращает исходный `FriendlyName` цели** и
`OutputName = t.Name` — то есть имя профиля в игре не меняется на «· FB …».

## 5. Резервная копия, запись, проверка, откат

Всё это — `MigrationTransaction` (`src/MigrationTransaction.cs`).
Папка по умолчанию: `Документы\Flight Bridge\Backups`
(`MigrationTransaction.DefaultRoot`). UI сейчас позволяет сменить путь (по принципу «Запустил и работает» это должно стать не больше мелкой вторичной ссылки, не шага главного сценария)
(`AutomaticApp`, файл предпочтений `%LocalAppData%\FlightBridge\backup-root.txt`).

### Перед записью

1. Мьютекс `Local\FlightBridgeMigration` — один перенос за раз.
2. Если есть сессия в состоянии `Pending` или `Restoring` — сначала нужно
   восстановление.
3. План должен быть `Ready`; цели уникальны; файлы не изменились с момента
   диагностики (`Engine.Unchanged`).
4. Цель должна быть **зарегистрирована**:
   - Steam: имя `inputprofile_*`, путь внутри `remote\`, имя должно быть упомянуто в `remotecache.vdf` (файл только **читается**, никогда не изменяется);
   - Store/WGS: файл внутри корня wgs, не `containers.index` / `container.*`,
     рядом есть `container.*`, в корне есть `containers.index`.
5. Копия не может лежать внутри игрового хранилища.
6. Для **каждого** магазина из плана делается **полный снимок всех файлов**
   (`Snapshot` + `File.Copy`) с SHA-256 каждого файла в журнале `transaction.xml`.
7. После копирования снова сверяют, что живое хранилище не изменилось.
8. Подготовленные выходные XML кладутся в `output-N` внутри сессии; журнал
   переводится в `Pending`.

### Атомарная запись

`Replace`: пишет во временный файл рядом с целью, затем `File.Replace`.
После каждой записи — повторный хеш и `Profile.Read`. При любой ошибке —
автоматический `Restore` той же сессии.

Успех → состояние `Completed`.

### Восстановление

`MigrationTransaction.Restore` / `RestoreCore`:

1. Проверяет целостность копии (`Verify` — все SHA-256 в снимке).
2. **Перед любым изменением** смотрит текущий хеш цели: если он не равен ни
   «до переноса», ни «после переноса» — значит пользователь (или игра) уже
   изменил профиль → **автовосстановление отказывается**, чтобы не затереть
   новые настройки.
3. Состояние `Restoring` → поочерёдный откат только файлов из списка `Change`
   → `Restored`.

Прерванный перенос (`Pending` / `Restoring`) блокирует новую запись в UI;
нужна кнопка «Вернуть настройки из последней копии».

Есть поддержка «legacy repair» (`NeedsLegacyRepair`) для старых журналов без
`AppVersion`, которые UI может сначала откатить и затем сразу сделать новый
перенос (`AutomaticApp.Transfer`).

### Чего программа никогда не делает с Store

- Не создаёт и **не переписывает** `containers.index`.
- Не трогает метаданные `container.*`.
- Пишет **только в уже существующий** зарегистрированный файл профиля 2024.
  Если нужного профиля в 2024 ещё нет — сначала его нужно один раз сохранить в
  игре (это же сказано в README и в сообщениях `Issues`).

## 6. Путь «экспорт для импорта» — есть в коде, UI им не пользуется

В `Engine.Export` и `Library.ExportBatch` (`src/Core.cs`, `src/Library.cs`)
реализован другой сценарий:

- пишут папку с `MSFS2024-migrated.xml`, `report.txt`, опционально
  `original-2020.xml` / `original-2024.xml` / `backup.xml`;
- явная фраза в отчёте: **«Программа не меняет файлы симулятора»** — пользователь
  должен сам импортировать XML через настройки управления MSFS 2024;
- `Library.ExportBatch` собирает несколько планов в сессию с файлом
  `НАЧНИТЕ ЗДЕСЬ.txt`.

Этот путь вызывается из **тестов** (`tests/CoreTests.cs`), но **не** из
`AutomaticApp`. Текущая кнопка переноса всегда идёт через
`MigrationTransaction.Execute` и **пишет в хранилище игры на месте**.

Файл `src/Main.xaml` в репозитории есть, но **не компилируется** в `build.ps1`
и не используется `App.Main` — интерфейс собирается кодом в `AutomaticApp`.

Установщик (`src/Setup.cs`) кладёт приложение в
`%LocalAppData%\Programs\FlightBridge`, создаёт ярлык в меню Пуск и ключ
удаления в реестре текущего пользователя. `DeviceCheck` (для установщика /
`/scan-test`) смотрит наличие папок данных игр и опрашивает HID/USB через WMI —
к логике переноса профилей не относится.

## Актуальный фасад Grok (ветка prog/export-default-core)

Кратко, простым языком — как работает перенос **сейчас** через `Migration`:

1. Программа **ищет** установки MSFS 2020 и 2024 на этом компьютере (Steam и Microsoft Store), не подставляя пути из сборки.
2. Если Steam-аккаунтов с профилями обеих игр несколько — сначала берёт активный, иначе «последний вход» из Steam; если всё ещё неясно — просит выбрать.
3. Строит **превью**: что будет скопировано в уже существующие профили 2024, что пропущено и почему (простыми словами).
4. Главный сценарий — **запись в игру** после вашего подтверждения; перед записью игры и Steam должны быть закрыты.
5. Сначала делается **полная копия** хранилищ в «Документы/Flight Bridge/Backups» с проверкой контрольных сумм.
6. Потом профили 2024 **переписываются по одному**; каждый файл проверяется; при ошибке всё **откатывается** из копии.
7. Служебный файл Steam Cloud (`remotecache.vdf`) **не изменяется**; после записи его контрольная сумма должна совпасть.
8. Если записать в игру нельзя — можно **сохранить файлы для ручного импорта** в настройках управления 2024.
9. Перенос однозначных клавиш KEY_* в другой раздел 2024 разрешён, но помечается предупреждением; «общий» профиль General — тоже с предупреждением.
10. Диагностика и отчёт **только читают** данные и не содержат полных путей и номеров аккаунтов.

Подробный разбор оригинального кода 0.5.1 — в разделах выше.
